# 设计规格结构

建立或修改项目规范时使用。目标是准确表达用户选择并指导实际样式，同时落实当前适用的品质目标。不要求填满所有类别或证明效率收益，也不因此开展完整可用性研究。

产品未知时，设计规范本身就是本次对象：完整展示排版、色彩、布局规则、组件状态与动态，不为填充预览而设计业务。具体值可采用明确标记的默认建议；产品架构保持未知。

## 五类配套产物

| 产物 | 职责 | 维护方式 |
| --- | --- | --- |
| `design.decisions.md` 或已有等价记录 | 用户意图、选择依据、范围、状态、替代关系与待同步项 | 决定的维护来源，见 [决策记录](decisions.md) |
| `design.md` 或已有等价规范 | 当前方向、设计原则、可执行条款、例外与检查方式 | 按来源引用基线、决定或项目约束；不复制维护决定历史 |
| 已有主题 / Token 文件；新项目可用 `design.tokens.json` | 可复用视觉值及语义角色 | 单一维护来源，见 [Token 约定](tokens.md) |
| `interaction.md` 或已有等价文档 | 当前涉及的操作、状态、反馈与行为约定 | 行为的维护来源，见 [交互规格](interaction.md) |
| 对应预览页，默认 `design.preview.html` | 将当前样式和代表性组件组合实际呈现 | 从上述来源派生，见 [预览约定](design-preview.md) |

文档开头提供交付对象、已获授权的范围、产品未知项、ByTaste 基线版本与相关 ID、实现建议来源、决策记录路径、相关决定 ID、Token、交互文档与预览入口。需要启动环境时写明打开方式。所有入口指向真实文件；尚未创建的产物明确标为缺失，不假装交付完成。

Agent 读取入口按决策记录约定维护。源码与文档冲突时先核对用户当前指令与有效决定，不凭文件名、修改时间或代码现状推断用户喜欢哪一版。

## 规范条款是主体

设计规范说明“怎样组织和表达才符合本项目的选择”。Token 负责取值，不能代替层级、布局、组件组合、内容和样式关系。

| 类别 | 项目条款示例 | 需要说明的边界 |
| --- | --- | --- |
| 信息与表达 | 保留用户选择的内容范围，减少无关装饰性说明 | 不以简洁为由删除已有必要标签、后果和恢复信息 |
| 层级与焦点 | 让选定的主信息获得约定程度的强调 | 并列内容可以有多个重点，不统一限定整页内容数量 |
| 分组与结构 | 用约定的间距、对齐或容器表达内容关系 | 不要求所有页面同一种卡片结构 |
| 密度与适配 | 在相关宽度保持选定的疏密感与内容完整性 | 明确窄屏、长内容和局部密度差异 |
| 视觉语义 | 相同角色沿用相同表达 | 引用 Token，不在多处抄写取值 |
| 组件使用 | 同类视觉结构复用已有组件和变体 | 新的表达需求可产生有范围的扩展 |
| 动效与反馈 | 按用户选择的表现强度呈现当前状态 | 行为见 interaction.md，时长和曲线引用 Token |
| 内容与素材 | 沿用约定的措辞、图像风格和资产 | 演示内容标明，不虚构客户或业务成绩 |

以上示例需按当前内容落实，不能整体复制成默认皮肤。强度、来源与用户认可分别处理：**必须**用于当前适用的 ByTaste 基线、用户明确要求或项目已采用标准；**应**用于有条件的约定；**可**用于可选策略。基线无须逐项批准，用户偏好也不会因已经实现而自动变为已选。

基线条款注明 ByTaste 版本与基线 ID，并在项目文件中写出实际关系及检查方式，不只留下依赖本机 Skill 路径的链接。用户条款引用真实决定 ID，项目约束引用原来源；具体参数与策略若未获指定则标为建议。已有规范表达了同一要求时关联复用，避免抄出第二套规则。

用户原有的明确功能要求与标准继续保留。省脑、可控、连续、恢复、轻快、无障碍与适应等基线按当前场景落实，写目标、适用条件与判断方式，不预先规定统一控件或技术。需要具体实现时再查 [体验品质知识](knowledge/experience-quality.md)，不将完整可用性研究或效率实验加成 ByTaste 门槛。

## 按需覆盖的规格维度

以 [六层概念地图](concepts.md) 检查是否遗漏重要关系。建立完整规范时简短注明相关层已有规则、当前建议、待定或不适用；不要求所有子概念都填值。保持本来的五类产物，不按概念再拆一套平行文件。

| 维度 | 本次需要记录什么 | 对照检查 |
| --- | --- | --- |
| 用途、用户与场景 | 已知的主要用途、目标用户、使用情境，以及页面、内容、平台和已有约束；未知项按需保留 | 是否有真实依据，是否把背景猜成审美或强迫补全？ |
| 当前设计方向 | 可复述的偏好、主导表达与陪衬关系、适用范围及相关决定 ID | 是否忠于用户，未定项是否仍未定？ |
| 原则与取舍 | 选定的表达目标、优先级与例外 | 能否解释为什么采用这个处理？ |
| 内容与结构 | 内容角色、语义分组、主次、叙述顺序、语气与代表性长度，见 [内容表达](knowledge/content-expression.md) | 是否体现选定结构，是否擅改功能？ |
| 布局与密度 | 信息主次、构图、区域关系、比例、对齐、分组、间距与适配条件，见 [布局规范](layout.md) | 长内容或窄屏是否破坏选定样式？ |
| 排版系统 | 字体角色、尺度、行长、节奏、换行、混排与数字，见 [排版知识](knowledge/typography.md) | 真实语言、长标题和回退字体下是否成立？ |
| 色彩系统 | 色板关系、语义配对、面积分配、强调范围，见 [色彩知识](knowledge/color.md) | 是否只给色值却未说明使用关系？ |
| 形状与表面 | 轮廓、嵌套、边界、深度、材质、光学协调，见 [表面知识](knowledge/shape-surface.md) | 实际组合和叠层是否协调？ |
| 图标与图像 | 资产角色、图标家族、摄影/插画指导、焦点、裁切、图文关系，见 [图像知识](knowledge/imagery.md) | 是否有实际资产依据，是否误把占位图当最终效果？ |
| 组件与内容模式 | 部件、变体用途、状态叠加、组合规则，见 [组件语法](knowledge/component-grammar.md) | 单个与成组、静态与变化时是否仍使用同一语言？ |
| 交互与动效 | 当前流程的理解、控制、连续、恢复与响应目标；保留表现强度，具体约定引用 interaction.md；方案选择见 [动效约定](motion.md) | 相关状态能否支持继续操作，是否与方向一致？ |
| 基础无障碍与适配 | 相关输入与辅助方式、已采用标准；不同内容、宽度、语言、已需主题中的保持项和变化，见 [情境适配](knowledge/adaptation.md) | 是否存在操作或信息障碍，是否新增了未要求的情境？ |
| 检查与同步 | 实际查看范围、用户反馈、来源修订与待同步项 | 哪些已经落实，哪些尚未确认？ |

### 推荐的正文组织

新建 design.md 时可以按下列顺序组织正文，已有结构能表达这些内容时直接沿用：

1. 范围与来源：当前对象、基线版本/ID、决定记录、Token、交互和预览入口。
2. 表达方向：当前偏好、主导与陪衬、必须保留的约束。
3. 内容与空间：角色、主次、分组、构图和密度的关系规则。
4. 视觉与组合：本次采用的排版、色彩、表面、资产和组件规则。
5. 动态与适配：视觉连续性、保持项、变化条件；具体行为引用 interaction.md。
6. 检查与待定：代表样本、实际检查结果、未确定及待同步的部分。

每条关键规则连接“真实依据（基线/决定/项目约束） → 适用对象/条件 → 具体关系 → 实现来源 → 预览样本”。没有用户明确指定的实现细节仍标为建议；用户偏好的采用状态引用决定记录，避免文档中维护多套状态。通常不需要为不适用的子概念建立空章节。

页面族规则增长到不易按需读取时才拆分，每份设计规范仍应有明确的对应预览。多份规范可共用一个决策记录与 Token 来源。

## 偏好摘要与决定引用

在 design.md 中保留一段用户能理解的当前方向，引用 `design.decisions.md` 的相关 ID。原话、选择情境和替代历史只在决策记录中维护。已有规范中的有效偏好按 [迁移约定](decisions.md) 接续，不能编造丢失的原始依据。

例如，以下是假设用户已经表达对应选择后的规范片段：

```text
当前方向：低装饰、较高信息密度，精致感来自排版与对齐。
决定来源：design.decisions.md 的 D-001、D-002。
范围：工作界面；官网尚未确定。
未定：具体字体与色彩温度；不得由“低装饰”自动补全。
规则：VIS-GROUP-01、VIS-DENSITY-01。
```

摘要跟随有效决定更新，不独立维护采用状态。规范中的更具体实现解释仍可标为建议；不能把“低饱和已选”扩大成“每个具体色值已确认”。

规范预览按 [默认质量基线](visual-quality.md) 检查。当前范围已观察到的层级混乱、归属错误、必要内容截断、状态不明等偏差先修复；无法修复时明确未完成。检查不扩展为效率或转化研究，也不能代替用户偏好反馈。

## 关键规则的表达

关键规则至少写明范围、具体要求和检查方式；必要时补充例外与理由。稳定的规则 ID 与决策 ID 分开：一个用户决定可能形成多个实施规则。

```text
规则：VIS-DENSITY-01
相关概念：信息密度；knowledge.density（知识依据，不是用户选择）
决定来源：D-001（用户选择列表紧凑，其他页面不变）
范围：订单列表内容区
要求：保留当前字段，采用紧凑的行间关系；沿用现有字号。
例外：窄屏允许内容换行，但不裁掉关键信息以强行维持行高。
取值：引用当前主题的表格密度变体；新取值仍标为建议。
检查：查看实际内容和长备注下的呈现，核对本条与相关 Token。
实现：未实施
偏好反馈：用户已选择方向；尚未评价这份具体实现。
```

这些是格式示例，不能复制成真实用户决定。是否完成按 [检查约定](verification.md) 判断，技术通过不自动转成用户喜欢。

## 共用规则与页面覆盖

先读取有效决定和共用规范，再读取匹配当前页面、区域或状态的明确覆盖。覆盖包含规则 ID、被覆盖的规则/决定 ID、作用域与用户依据。没有明确关系的冲突不能靠文件顺序解决。

例如，全局疏朗而对账列表紧凑时，只有该列表密度覆盖共用规则，不影响其字号、色彩或其他页面。新的局部选择不使旧全局决定整体失效。用户明确改变全局方向时，更新决定的替代关系、当前规范与受影响产物。

## 参考与来源

只记录影响实际决定的材料，说明位置、观察范围与用途。例如“参考 R1：截图顶部筛选区；用户喜欢它的紧凑；无法从截图确认交互”。引用研究或指南时保留适用条件；用户喜欢、参考观察、Agent 解释不能合并成一个来源。

数值在 Token 来源维护，行为在 interaction.md 维护。决定变更后更新相关引用和预览；只修改历史说明且未改变有效设计时，不重建无关产物。
